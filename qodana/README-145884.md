# Qodana quality gate: Large Class

**145884 - Lukasz Swiecicki**

This gate detects instances of Fowler's **Large Class** smell in BattleShip2 with Qodana for JVM
(Community), run from GitHub Actions. It approximates the **God Class** detection strategy from
Lanza & Marinescu, *Object-Oriented Metrics in Practice* (2006). The book describes God Class as
"comparable to Fowler's Large Class bad smell" (p. 80).

## Detection strategy in the book

    GodClass = (ATFD > FEW) AND (WMC >= VERY HIGH) AND (TCC < ONE THIRD)

(Fig. 4.5 p. 57 and Fig. 5.2 p. 81; Java thresholds from Table 2.2 p. 16: WMC very high = 47,
NOM/class very high = 15.)

## Mapping table: Fowler smell to Qodana inspections

| Fowler smell | Book condition | Inspection in the IDE | Inspection ID | Metric / limit used (IDE default) | Limitations |
|---|---|---|---|---|---|
| Large Class | WMC ≥ VERY HIGH (47) | Overly complex class | `ClassComplexity` | WMC, `m_limit` = 46 (80) | Absolute threshold, not relative to the system |
| Large Class | none (size proxy) | Class with too many methods | `MethodCount` | NOM, `m_limit` = 14 (20) | Not part of the book's rule; also counts interfaces, tests and getters |
| Large Class | ATFD > FEW | none | none | none | No inspection measures access to foreign data |
| Large Class | TCC < ONE THIRD | none | none | none | No inspection measures class cohesion |
| Large Class | AND of the three conditions | none | none | none | Each inspection reports on its own, so no AND is possible |

An inspection reports a class when the metric **exceeds** `m_limit`. That is why the book's
"WMC ≥ 47" is written as `m_limit` = 46, and "NOM ≥ 15" as `m_limit` = 14.

Quality gate in `qodana-145884.yaml`: `failureConditions.severityThresholds.any`.

## Provoking the smell (step 9)

The first commit adds a deliberately large class, `src/main/java/battleship/LargeClassDemo.java`,

## Blocking the merge (step 10)

A branch protection rule on `main` requires this gate's status check (job `qodana` of the workflow
*Qodana smell gate 145884 (Large Class)*) to pass before a pull request can be merged. While the gate
was red on [PR #40](https://github.com/LEI-145884/Battleship2/pull/40), GitHub blocked the merge.
After `LargeClassDemo` was deleted, the gate turned green and the merge was allowed again.

## Why an XML profile

The first version used the YAML profile from Listing 3 (`base: name: empty` plus two inspections).
In every run Qodana logged `Inspecting with the 'Default' profile` and reported 196 unrelated
problems. The run logs (`qodana-report` artifact, `log/main.profile.xml`) showed two causes:

1. **Wrong IDs.** Inspectopedia shows `ClassWithTooManyMethods` and `OverlyComplexClass` under
   "By ID", but the linter's actual IDs are `MethodCount` and `ClassComplexity`. Unknown IDs are
   ignored without any error.
2. **The base profile was ignored.** The effective profile was built as
   `qodana.main.profile(base:Default)` instead of `empty`.

The XML profile lists every inspection of this linter (1675 of them) explicitly and disables all of
them except the two used here, so it does not depend on the base profile. After this change the log
showed `Inspecting with the 'LargeClass-145884' profile` and only the two inspections ran.

## Reflection

The gate correctly found the two real Large Classes in the project. `Game` (WMC 67, 22 methods)
handles rendering, JSON, input parsing, shot generation and statistics in one class, and `Ship` is
flagged by both metrics as well. `MethodCount` also produced false positives: two interfaces, which
have no logic, four test classes, and `Position`, which is mostly getters. Possible false negatives
are classes with a few very large methods, or classes that mainly use other classes' data. The
result depends heavily on the thresholds: with the IDE defaults (WMC 80, NOM 20) no class would be
flagged for complexity, and only `Game` and two test classes for their method count; the outcome
also changes from fail to pass just by moving `any` from 0 to 11. Compared with the book's strategy, Qodana has no ATFD or TCC and cannot combine conditions
with AND, so it measures size and complexity but cannot tell a God Class from a large but cohesive
class.
